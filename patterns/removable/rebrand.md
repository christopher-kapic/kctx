# Rebranding the PWA

Replace every user-visible "starter" string and icon with your own app name, colors, and artwork. Written so a nontechnical owner can paste the steps into an AI agent and end up with a cleanly rebranded PWA.

> **This doc is the PWA display layer.** It is part of the default branding path in [agent-tasks/rebrand.md](../agent-tasks/rebrand.md), alongside the TOTP issuer and public README identity. Internal package, database, container, and volume renames are optional and do not gate onboarding. Use this doc for the PWA shell (manifest, icons, offline page, cache busting).

## Pre-rebrand checklist

Decide all of these before touching any files. The agent will need every value.

- **App name** — the full name shown in the browser tab and PWA install prompt. Keep it under ~30 characters so it doesn't get truncated.
- **Local subdomain slug** — lowercase letters, numbers, and hyphens only, e.g. `acme`. Local dev will use `https://<slug>.localhost` for the web app and `https://api.<slug>.localhost` for the API. Pick a slug that is unique on the developer's machine so multiple projects can run at once.
- **Short name** — the label under the home-screen icon on iOS and Android. Keep this **under 12 characters** or it will be ellipsized on most phones. If you don't have a short version, reuse the full name.
- **Description** — one sentence describing the app. Used in the install prompt and in the `<meta name="description">` tag.
- **Theme color** — hex value (e.g. `#0c0c0c`). This colors the address bar on Android and the status bar background on installed PWAs. Pick something that matches your brand and reads well in both light and dark mode.
- **Background color** — hex value used for the splash screen shown while the PWA is launching. Usually the same as theme color, or your app's primary background.
- **Icon source** — a single **512x512 PNG** of your logo on a solid (non-transparent) background. All other icon sizes are derived from this. Make sure the logo has at least ~10% padding from the edges so it isn't cropped by maskable-icon round/squircle masks on Android.

## Files to update

Every file below contains a literal `starter` string that a user can see. Replace each one with the values from the checklist above.

### 1. `VITE_APP_NAME` env var (`apps/web/.env`)

The PWA manifest's `name`, `short_name`, and `description` are derived at build time from `VITE_APP_NAME`; the runtime app shell reads the same value. Set it in `apps/web/.env`:

```bash
VITE_APP_NAME=Your App
```

That rebrands the install prompt, the browser tab title (via `__root.tsx`, which also reads this var), and any place the web app renders the app name. No code edit needed for the name itself.

**For deployment, set it where the bundle is built — not just at runtime.** `VITE_APP_NAME` is inlined into the SPA at build time, so setting it on a running container has no effect. `Dockerfile` declares the matching `ARG VITE_APP_NAME` (defaulting to `""`, which falls back to `"App"`), so pass it as a build arg: `--build-arg VITE_APP_NAME=…`. Dokploy does **not** auto-forward an Application's env vars into the Docker build — add it to the Application's build args. Changing it requires a **rebuild**, not a restart. See [patterns/deployment-vps.md](../deployment-vps.md).

### 2. Local portless subdomains

Update `portless.json` so local dev uses the chosen slug:

```json
{
  "script": "dev:raw",
  "apps": {
    "apps/web": { "name": "<slug>" },
    "apps/server": { "name": "api.<slug>" }
  }
}
```

Then set the root `.env` auth callback URL to the browser-facing local origin:

```env
BETTER_AUTH_URL=https://<slug>.localhost
```

Vite reads `portless.json` to derive the default API proxy target, so there is
no second hostname to edit in code. Leave `VITE_SERVER_URL`, `VITE_DEV_PORT`,
`VITE_DEV_SERVER_URL`, and `SERVER_PORT` unset for normal portless dev.

**The example values in `.env.example` live in the manifest, not in the file.**
`.env.example` is generated by `pnpm env:sync` from `scripts/lib/env-manifest.ts`,
so editing it directly is reverted by the next sync and fails CI's `pnpm env:check`
in the meantime (`✗ .env.example is out of date`). Update the manifest entries
that still carry the template's identity, then run `pnpm env:sync`:

| Manifest entry | Template value | Change to |
| --- | --- | --- |
| `BETTER_AUTH_URL` → `example` | `https://starter.localhost` | `https://<slug>.localhost` |

Keep the `DATABASE_URL` example and local database name unchanged for display
branding. Change them only as part of an explicitly chosen database rename.

If you rename the local database (the `/starter` path segment of `DATABASE_URL`),
the local-database guard (`scripts/assert-local-database.sh`) will refuse
`pnpm db:push` / `pnpm db:seed` until you export `EXPECTED_DB=<name>` — see
[schema-changes-recipe § The two commands you need](../schema-changes-recipe.md#the-two-commands-you-need).

### 3. `apps/web/vite.config.ts` — theme + background colors only

The VitePWA manifest block still hardcodes the two colors:

```ts
manifest: {
  name: appName,
  short_name: appName,
  description: `${appName} - PWA Application`,
  theme_color: "#0c0c0c",             // → your theme color
  background_color: "#0c0c0c",        // → your background color
},
```

Only edit the two colors. `name`/`short_name`/`description` are driven by `VITE_APP_NAME` above — leave them alone unless you want a description that diverges from the default `${name} - PWA Application` template.

> These two hex values are the **PWA chrome color only** (address bar + splash). They are not the app's color palette. To restyle the actual UI — buttons, backgrounds, focus rings, dark mode — change the OKLCH theme tokens in `globals.css` per [../shadcn-theme-update.md](../shadcn-theme-update.md), then set these two hex values to match your new `--background`/brand.

### 4. `apps/web/src/routes/__root.tsx` — usually nothing to edit

This file owns the document `<head>` (TanStack Start renders the HTML — there is no `index.html`), and both values it emits are already derived, not hardcoded:

- **`title`** reads `VITE_APP_NAME` — covered by §1.
- **`description`** comes from the `errors:pageDescription` i18n key with the app name interpolated (`{{appName}} is a web application`, per locale in `packages/locales/src/<lang>/errors.json`). If you want a real one-sentence description instead of that generic template, edit the `pageDescription` value in **every** locale's `errors.json` (or change the English one and re-run `pnpm i18n:translate` after deleting the stale translations — see [i18n](../i18n.md)).
- **Do not add a `theme-color` meta tag here.** The file intentionally declares none — theme color is managed imperatively so it can track light/dark mode. The runtime light/dark hex pair lives in `packages/config/src/theme-init.ts` (the anti-FOUC script that creates the meta on first paint) and `apps/web/src/hooks/use-theme-color-meta.ts` (keeps it in sync on theme toggles) — the two must stay in lockstep, mirroring `--background` in `globals.css`. The install-time manifest hexes live in `vite.config.ts` (§3).

### 5. `apps/web/src/components/header.tsx` — nothing to edit

The visible app-name link in the top header reads `env.VITE_APP_NAME` unconditionally (the env schema defaults it to `"App"` when unset). Setting the env var in §1 is the whole change; there is nothing to wire up in this file.

### 6. `apps/web/public/offline.html`

The offline fallback is a static file shipped before the JS bundle, so it can't read `VITE_APP_NAME`. The title is intentionally generic (`<title>Offline</title>`) so the file works for any rebrand. For app-specific branding here, either hand-edit on every rebrand or move the offline fallback into the SPA bundle (more involved). If you changed the theme/background colors, update the inline `background: #0c0c0c` and `color: #e5e5e5` styles to match.

### 7. `apps/web/public/` icon files

Replace these binary files with versions generated from your 512x512 source (see "Icon regeneration" below):

- `favicon.ico` — browser tab favicon
- `apple-touch-icon-180x180.png` — iOS home screen icon
- `pwa-64x64.png` — small PWA icon
- `pwa-192x192.png` — Android home screen icon
- `pwa-512x512.png` — splash screen / large icon
- `maskable-icon-512x512.png` — Android adaptive icon (must have safe-zone padding so the round mask doesn't crop the logo)
- `logo.png` — the source image referenced by `apps/web/pwa-assets.config.ts`. Replace this with your 512x512 source so future regenerations use the new artwork.

Keep the **filenames identical** — they are referenced by VitePWA, the manifest, and `__root.tsx`. Only the contents change.

### 8. (Optional) `apps/web/pwa-assets.config.ts`

This file points the asset generator at `public/logo.png`. If you keep that filename, you don't need to edit it. If you renamed your source image, update the `images: [...]` line.

## What this doc deliberately does not cover

The broader choices below belong to [agent-tasks/rebrand.md](../agent-tasks/rebrand.md), which separates display branding from optional internal maintenance and requires `pnpm verify`:

- The internal package scope (`@starter/ui`, `@starter/api`, `@starter/db`, …), `package.json` `name` fields, and the matching tsconfig path aliases — a repo-wide rename touching every import.
- Database, container, and volume names in the two docker-compose files.
- The TOTP `issuer` shown in users' authenticator apps (`packages/auth/src/index.ts`).
- `README.md`, `SECURITY.md`, `infra-notes.md`, and template-provenance cleanup (the license).

Complete the TOTP issuer and public README identity through the default path there. Keep internal names stable unless the user explicitly chose to rename them; retained internal names do not make display branding incomplete.

## Icon regeneration

Two options for generating the icon set from your 512x512 source:

1. **Manual export** — open your logo in Figma, Sketch, or any image editor, export at each size listed above, save with the exact filenames and overwrite the files in `apps/web/public/`. Make sure `maskable-icon-512x512.png` has ~10% padding inside a safe circle.
2. **Automated** — CLIs like `pwa-asset-generator` and `@vite-pwa/assets-generator` take a single source image and emit the full set. This repo already has `pwa-assets.config.ts` wired up for the latter. Ask your agent to look up the current invocation if you go this route — do not install anything blindly.

Either way the end state is the same: every file in the list above replaced with your branded version, same filenames.

## Rebuild and redeploy

Once the strings and icons are updated:

```bash
pnpm build
```

Then deploy as usual (see [deployment-vps.md](../deployment-vps.md) for the Dokploy-on-VPS deployment recipe).

**Cache busting warning.** Service workers cache aggressively. Users who already have the old PWA installed will not see the new icon, name, or splash screen on the next launch — the OS caches the manifest at install time, not on every load. To pick up a rebrand, an existing user must:

1. Open the PWA at least once after deploy so the new service worker activates.
2. **Uninstall** the PWA from their home screen.
3. Reopen the site in their browser and **reinstall** it.

There is no way around this; it is how every operating system handles installed PWA metadata. Communicate this to your users before you ship the rebrand. New users (anyone who installs after the deploy) will get the new branding immediately and don't need to do anything.

## Verification checklist

After deploying, walk through this list on a real device (not just desktop devtools):

- [ ] Browser tab title shows the new app name.
- [ ] `view-source:` of the page shows your new `<meta name="description">`. (There is **no** `theme-color` meta in the source — it's created at runtime by the theme-init script.)
- [ ] In devtools → Elements → `<head>`, the runtime `<meta name="theme-color">` is present and its `content` flips between the dark and light hex when you toggle the app theme.
- [ ] `https://your-domain/manifest.webmanifest` loads and contains the new `name`, `short_name`, `description`, `theme_color`, and `background_color`.
- [ ] `https://your-domain/favicon.ico` returns your new favicon.
- [ ] Install the PWA fresh on iOS — home screen icon, label, and splash screen are all correct.
- [ ] Install the PWA fresh on Android — home screen icon (including the maskable adaptive icon), label, and splash screen are all correct.
- [ ] The header on every page shows the new app name (not "Starter").
- [ ] Disable the network and trigger a navigation — the offline fallback page shows the new title.
- [ ] Check remaining `starter` references against the selected scope. Public copy and the TOTP issuer must match the chosen name; internal imports and database/container names are expected to remain for the default display path.
