# Removable internationalization (i18n)

> **Why this is still a manual recipe.** The removal engine (`pnpm template:remove …`) automates leaf features whose edits are anchored file deletions and registration unwiring. i18n is not that: it re-parents every route out of `apps/web/src/routes/$lang/`, rewrites every `Link to="/$lang/…"` and `params.lang`, inlines the English copy for every `t()` call across the whole web app, replaces the locale-aware Zod error map, and edits AGENTS.md's STOP rules (the t()-coverage gate and rule 8 exist only while i18n does). That is a semantic rewrite of the application, not a mechanical transform — a wrong automation would compile-looking-break every screen. Until that becomes an anchored transform (it would need the engine to run the web build and regenerate `routeTree.gen.ts` from moved files), this doc remains the reviewed manual procedure, and the steps below are the inventory.

The starter ships full i18n wired up: react-i18next + browser language detection, a `/$lang/...` URL prefix enforced by `apps/web/src/routes/$lang.tsx`, JSON bundles in the shared `@starter/locales` package (`packages/locales/src/<lang>/*.json`), a locale-aware Zod error map, a per-user `locale` field in the database, and a `pnpm i18n:translate` script that fills missing bundle keys via OpenRouter or Anthropic. Locale constants are shared between server and client via `@starter/config/locales`. Translation is bundle-only — there is no database or content auto-translation.

> **Keeping the Expo app?** The `@starter/locales` package is a shared source of truth: the web app consumes its per-namespace bundles and the Expo app consumes the `native` namespace (`packages/locales/src/native.ts`, statically imported — see [native.md](../native.md)). This removal doc rips out **web** i18n only. If you keep `apps/native`, do **not** delete `packages/locales` or its `i18next` / `react-i18next` catalog entries — decide separately whether the app stays localized (keep the package, native.json bundles, and native i18n wiring) or becomes English-only (then also follow the native-i18n teardown, or remove the Expo app entirely via [removable/native.md](./native.md)). The steps below assume a web-only product; adjust each package/catalog deletion accordingly when native survives.

For single-locale apps — internal tools, English-only products, anything not shipping a second language — none of this is needed, and the surface is large enough that carrying it makes every new component more expensive (every string becomes a key + a translation round-trip).

## When to remove

You should be confident you will **never** add a second locale. Removing i18n is more invasive than the other removable patterns because it touches every UI surface. Re-adding it later is a large refactor.

Conversely, **keep** i18n if any of the following apply:

- You ship to users in more than one language.
- You may add a second locale in the foreseeable future.
- Your audience includes users whose browsers report a non-English `navigator.language`, even if all your copy is currently English — the framework's presence is what makes the next locale a one-day project instead of a one-month one.

## What removing loses

- **Multi-locale routing.** The `$lang` prefix and the `decideLocaleRedirect` logic go away. URLs become `/dashboard` instead of `/en-US/dashboard`.
- **Locale-aware Zod error map.** Validation messages return whatever you hardcode in each schema.
- **The `pnpm i18n:translate` script.** All UI copy lives in one set of files, edited by hand.
- **The `user.locale` field.** Per-user locale preference is meaningless without multiple locales.

## Removal steps

> **Heads up:** this removal touches every component file that currently calls `useTranslation()` or `t()`. Plan for a full grep-and-replace pass across `apps/web/src/`.

Before changing anything, inventory the complete deletion and shared-edit set below and run `git status --short --untracked-files=all`. Refuse if any planned path overlaps existing work. The owner must explicitly choose this URL-changing feature removal. Preview each exact tracked deletion set with `git rm --dry-run`, then repeat without `--dry-run` only after reviewing it; never use force flags or recursively sweep ignored/untracked local files. Complete all dependent edits as one verified change.

1. **Remove the locale URL prefix.** Move every route file out of `apps/web/src/routes/$lang/` up one level to `apps/web/src/routes/`. Delete `apps/web/src/routes/$lang.tsx`. Update every `Link to="/$lang/..."` in the codebase to drop the prefix, and remove `params.lang` from any route loaders or `beforeLoad` callbacks.
2. **Delete the web i18n module** (and the `@locales` Vite alias + tsconfig path that point at the locales package).
   ```sh
   git rm --dry-run -r -- apps/web/src/i18n
   ```
   The preview includes `index.ts`, `config.ts`, `zod.ts`, `I18nReady.tsx`, `labels.ts`, `redirect-to-default.ts`, `use-namespace-t.ts`, and the tests. The JSON bundles now live in `packages/locales/` — if native is gone too, preview `git rm --dry-run -r -- packages/locales`, remove that reviewed tracked set, and drop the `@starter/locales` dependency from `apps/web/package.json`; if native stays, leave the package in place (the web app just stops importing it). **If you delete `packages/locales`, also remove its hand-enumerated install line** — `COPY packages/locales/package.json packages/locales/` — from the `builder` *and* `prod-deps` stages of *both* `Dockerfile` and `Dockerfile.worker` (four lines in total). A stale line fails `docker build` at install time; `pnpm docker:check-copy` (the CI `lint` gate) catches the omission.
3. **Unwire `I18nReady` and the i18next provider** from `apps/web/src/client.tsx`, `apps/web/src/server.ts`, and `apps/web/src/router.tsx`. Remove `localeModulePreloadUrl` from router context / `__root.tsx` modulepreload links, delete `apps/server/src/locale-modulepreload.ts` (+ test), and remove the `loadLocaleModulePreloads` / `x-locale-modulepreload` wiring from `apps/server/src/index.ts`. Drop the `locale-<tag>` `manualChunks` rule and the `LOCALE_CHUNK_PREFIX` constant. If nothing else needs the client Vite manifest, drop `build.manifest: true` from `apps/web/vite.config.ts` **and** the `/.vite/*` deny route (plus `static-manifest-privacy.test.ts`) that exists only to keep that manifest off the public origin. The app should boot without waiting for i18next initialization.
4. **Replace every `t()` call with the literal English string.** Grep is your friend:
   ```sh
   grep -rn "useTranslation\|\bt(" apps/web/src packages/ui/src --include='*.ts' --include='*.tsx'
   ```
   Then remove the `useTranslation` imports and inline the strings. For Zod schemas, replace the locale-aware error map with hardcoded messages on each field.
5. **Drop the catalog dependencies.** In `pnpm-workspace.yaml` under `catalog:`, delete:
   ```yaml
   i18next: ...
   react-i18next: ...
   i18next-browser-languagedetector: ...
   ```
   And remove them from every `package.json` that lists them.
6. **Defer the `user.locale` drop on a deployed app.** First finish and deploy the runtime removal with the field retained in Prisma, then verify no consumer still uses it. Remove the field only in a separate approved contract release under [schema changes § Drop a column](../schema-changes-recipe.md#drop-a-column). Dokploy's code-only release keeps the leader `safe` and followers `off` + `WAIT_FOR_SCHEMA=true`; the later manual dangerous contract returns the leader to `safe` after confirmation cleanup. Do not remove the field early and disable the schema gate to accommodate the mismatch.
7. **Remove or replace the shared locale constants.** `packages/config/src/locales.ts` is imported well outside the web i18n layer: `packages/auth/src/signup-locale.ts` and `verification-callback.ts` (the stored user locale), `packages/api/src/routers/auth.ts`, `apps/server/src/{cors-headers,ssr-cache,seo,locale-modulepreload}.ts` (the locale request header, SSR cache key, and hreflang/sitemap output), `apps/web/vite.config.ts` + `apps/web/src/{router.tsx,lib/auth-client.ts}`, and — if you keep the Expo app — `packages/locales/src/native.ts` and `apps/native/`. `packages/mailer/src/locales/` keeps its own hand-synced copy of the list. If any locale-bearing model or the Expo app survives, do **not** blindly delete the file. Instead, collapse it to a single supported locale (for example `en-US`) and update call sites to treat locale as fixed. Delete the file only after `rg "SUPPORTED_LOCALES|DEFAULT_LOCALE|@starter/config/locales"` proves no remaining package imports it.
8. **Remove the translate scripts.** Delete `scripts/translate-locale-bundles.ts` and the `i18n:translate` + `i18n:translate:mailer` entries in `package.json`.
9. **Remove the translation provider env vars.** In `packages/env/src/vars/shared.ts` (the worker-safe declarations — these live there, **not** in `vars/server.ts`, because `@starter/i18n-translate` and the worker import `@starter/env/shared`), delete `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `TRANSLATION_PROVIDER`, `TRANSLATION_MODEL` (unless you use them for other purposes — many forks do not).

    **Check every other consumer before you touch the deploy config.** `OPENROUTER_API_KEY` / `ANTHROPIC_API_KEY` are shared keys — the chat add-in reads `OPENROUTER_API_KEY` too — so they are only dead once nothing else in your app uses them. On the Dokploy/VPS setup ([deployment-vps.md](../deployment-vps.md)) remove the same vars from both the server and worker Applications' env config.

    **When you do remove them, delete their `ENV_VARS` entries (and the `translation` group) from `scripts/lib/env-manifest.ts` and run `pnpm env:sync` — do not hand-edit `.env.example`.** Those files are generated from the manifest, so a manual deletion is reverted by the next sync; `pnpm env:check` gates both directions in CI (a schema key with no manifest entry, and a manifest entry naming a key no schema declares). Verify with `pnpm env:check`.
10. **Update `AGENTS.md` and the patterns index (CRITICAL — do not skip).** Open `AGENTS.md` and:
    - Delete the entire `### Internationalization (i18n) — no hardcoded strings` section, including the new-feature locale-generation bullet that ends with the HTML comment `<!-- removable-i18n: ... -->`. Search for `removable-i18n:` to locate it.
    - In the `## Stack` paragraph, delete the `i18n (`/$lang/...`)` item.
    - In `## Sitemap`, delete the sentence `All routes are `/$lang/...` ([i18n](./patterns/i18n.md)).`
    - **In `## STOP`, edit rule 8** — it reads "every user-facing string goes through `t()`". Remove that clause. STOP overrides every pattern doc, so leaving it in means the agent keeps reintroducing `t()` into a repo that no longer has it. This is the single most important edit in this step.
    - Then run `pnpm sync:agent-docs` to propagate the changes to `CLAUDE.md` and `.cursorrules`.

    In `patterns/README.md` (the categorized patterns index), delete the rows pointing at [i18n.md](../i18n.md) and [removable/i18n.md](./i18n.md), and delete both files.
11. **Final grep + rebuild + boot.**
    ```sh
    rg "useTranslation|\\bt\\(|SUPPORTED_LOCALES|DEFAULT_LOCALE|@starter/config/locales|i18next|react-i18next" apps packages
    pnpm install
    pnpm build
    pnpm test
    pnpm knip
    pnpm docker:check-copy   # only if you deleted packages/locales
    ```
    Knip will flag any stray `i18next` imports or unused exports. Build will fail if a component still calls `t()` against a deleted import. Boot the app once after the build; a route-level locale redirect left behind can pass typecheck and still break navigation.

## Restoring i18n

If you remove i18n and later need it back, the cleanest path is to copy the deleted files from a fresh `git clone` of the starter at the same version you forked from, then re-apply your own changes to the route files. There is no incremental "add a single locale" path that is shorter than restoring the full framework — the `/$lang/...` routing contract is load-bearing for the detection chain.

If you deleted the translation provider env vars in step 9, re-declare them in `packages/env/src/vars/shared.ts`, re-add their manifest entries and the `translation` group in `scripts/lib/env-manifest.ts`, and run `pnpm env:sync` so `pnpm i18n:translate` can authenticate again.

If you deleted `packages/locales`, re-add its `COPY packages/locales/package.json packages/locales/` line to the `builder` and `prod-deps` stages of both `Dockerfile` and `Dockerfile.worker` (in alphabetical position); `pnpm docker:check-copy` will flag them as missing until you do.
