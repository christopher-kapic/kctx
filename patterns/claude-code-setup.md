# Claude Code setup — project hooks and the trust prompt

This repo ships a `PreToolUse` hook that blocks the commands on the
[AGENTS.md](../AGENTS.md) Dangerous Commands list at the tool boundary, before
Claude Code runs them. The hook rules are tracked in `scripts/claude-hooks/`;
the small `.claude/settings.json` that turns them on is personal (gitignored)
and is generated by `pnpm run setup`, or on its own with:

```bash
pnpm claude:hooks:install
```

Run that once per clone. Because the settings file only points at the tracked
script, `git pull` updates the rules without reinstalling.

If you already have your own `.claude/settings.json`, the installer **merges**
into it rather than overwriting: it appends the PreToolUse entries that are not
already there and any missing `permissions.deny` prefixes, and leaves everything
else you have configured alone. It never removes or rewrites your settings. It
tells you what it added; if there was nothing to add it says so and exits. The
one case it will not touch is a file that is not valid JSON — it prints the
parse error and asks you to fix it (or delete the file and re-run). `pnpm doctor`
reports when your installed copy has drifted from
`scripts/claude-hooks/settings.json`.

Claude Code's `.claude/settings.local.json` has higher precedence. The
installer deliberately does not rewrite that personal file, but it exits with
a diagnostic when the file is invalid JSON or sets `disableAllHooks: true`; in
either case `pnpm doctor` gives the same warning. Remove that local override
yourself, then rerun the installer. The hook protects both settings files from
direct agent writes, but this is still mistake prevention rather than
same-identity isolation.

Cursor and GitHub Copilot cannot be blocked at that boundary. For those
harnesses the backstop is `scripts/policy-checks.sh` (CI + lefthook pre-commit).

## The trust prompt is a feature

The first time Claude Code opens this repo it will ask you to **trust** the
project's `.claude/settings.json` hooks. That prompt is expected. The hooks are
the only thing standing between an agent and `prisma migrate reset` against
whatever `DATABASE_URL` happens to be in the shell.

Allow the project hooks. If you skip the prompt, Claude Code still has the
`permissions.deny` prefixes, but the hook is what catches `git commit -m x
--no-verify` (deny rules are prefix-only) and edits to generated files.

This is documented here so getting-started does not treat the prompt as
suspicious or as something to click through blindly — it is the safety net
turning on.

## What the hooks block

`scripts/claude-hooks/pre-tool-use.sh` runs on every `Bash` and `Write`/`Edit` call. It
is a thin wrapper that hands the payload to `scripts/claude-hooks/pre-tool-use.mjs`,
where the rules live so they can be tested: `pnpm policy:hooks` runs the
built-in self-test and is part of `pnpm verify:tooling` (nightly + release).
If Node is missing, the
hook fails closed and denies the call.

**Bash** (stderr message + exit 2 = deny):

- `prisma migrate reset|dev|deploy`
- `--force-reset`
- `prisma db drop`
- `--accept-data-loss` typed directly (the sanctioned wrappers `pnpm db:push:dangerous` / `scripts/db-push-dangerous-local.sh` pass it internally and are still allowed)
- `dropdb`
- `--no-verify`
- `git push --force` / `git push -f` (`--force-with-lease` is not blocked)
- `git reset --hard` (use `git stash`, or `git restore <one file>`)
- `git clean -f` / `-d` / `-x` (`git clean -n` is fine)
- forced `git checkout` and working-tree `git restore` outside one static file —
  broad pathspecs and directory targets (`git checkout .`, `git checkout HEAD .`,
  globs, trailing `/`), with or without `--`, can discard more work than the
  agent can recover (use `git restore <one file>` or `git stash`)
- `docker compose down -v` / `--volumes` — except the exact local dev stack: the one
  repository-root `docker-compose.dev.yml` file (spelled `docker-compose.dev.yml` or
  `./docker-compose.dev.yml` while the command cwd remains the project root), default
  project name (`starter-dev`), no extra compose files, and no Docker `--context` /
  `--config` / `--host` / `--debug` overrides. The sanctioned spellings are
  `bash scripts/compose.sh -f docker-compose.dev.yml down -v` and `docker compose -f
  docker-compose.dev.yml down --volumes`. The hook proves that cwd per executing
  scope: current-shell `cd`/`pushd`/`popd` and `eval`, loop re-entry, and a possible
  Bash `lastpipe` final stage withhold this narrow exception; subshells, command
  substitutions, and shell `-c` children do not taint their parent.
- `rm -rf` on anything that is **not** build output or a cache (`node_modules`, `dist`, `build`, `.turbo`, `coverage`, `/tmp/...` are allowed; `find <disposable dir> … -exec rm -rf {} +` is allowed, judged on the find root)
- `sudo`, `doas`, `su`, or `runuser` — as the command actually being run,
  including inside `$(…)`; the hook does not model host-specific privilege or
  shell-wrapper grammars
- a noninitial pipeline stage that is a shell (`producer | sh | cat` is still
  blocked) or a recognized interpreter reading program text from stdin
- a recognized shell reading program text from stdin directly, including
  here-strings, heredocs, redirected files, or shell `-s`; use a reviewed
  source file instead
- inline program-text modes such as Node `-e`/`--eval`/`-p`/`--print`, Python
  `-c`, and their finite recognized equivalents. The hook rejects the source
  boundary rather than pretending to inspect JavaScript or another language.
  Put reviewed source in a file; its execution still needs capability limits
  supplied by the agent harness or OS, which this repository hook does not
  install.
- Docker `volume rm` / `volume prune` and `system prune --volumes`
- `cp`/`mv` whose **destination** ends in `.bak` / `.old` / `.orig` / `.backup` (`mv notes.old.md docs/` is fine); Write/Edit of those suffixes is denied too
- `DROP TABLE|DATABASE|SCHEMA` / `TRUNCATE` / `DELETE` without `WHERE` in a `psql`,
  `mysql`, or `prisma db execute` invocation with inline `-c` / `--command` /
  `-e` / `--execute` payloads

Each rule judges one command *segment* at a time (`git push && rm -f tmp.txt`
is a push and a delete, not a force push), reads *tokens* rather than raw text
(so a banned flag quoted inside a commit message is not a denial), skips
read-only segments (`grep "migrate deploy" patterns/`), and unwraps
`bash -c "…"` / `sh -c "…"` / `eval "…"` payloads so a nested command is judged
on its contents.

For every protected/generated target, the CST carries a static output redirect
through enclosing lists, control forms, and pipeline stages to the same
protected-write check. Direct static `rm`, `unlink`, `rmdir`, and `mv` source
operands also pass the policy-integrity check; removing a containing directory
is rejected when it contains a protected asset.

The bounded wrapper grammar also permits the read-only `command -v` / `-V`
queries and treats `command -p` as execution of the effective command. `npx
-y` / `--yes` is parsed as its Boolean form so the effective command still
receives the same checks; it does not waive the separate AGENTS.md requirement
to ask before installing a dependency.

### Known limits

The hook is a tool-boundary net, not a shell interpreter. It does not see:

- **Heredoc bodies.** One bounded writer form is allowed: a standalone bare
  `cat` with exactly one single- or double-quoted alphanumeric delimiter, a
  CST-literal body (no expansion children), and exactly one static `>` target,
  in either order (`cat <<'EOF' > file` or `cat > file <<'EOF'`).
  The target still passes the enforcement-asset write check. Pipelines,
  conditionals, loops, append/descriptors, unquoted or dynamic delimiters,
  non-`cat` consumers, additional arguments, and every other heredoc shape are
  rejected. Recognized shell stdin is always rejected, so this is not a general
  heredoc or interpreter-input allowance.
- **Tree-sitter parse boundaries.** Bash source must parse to an error-free
  Tree-sitter CST. Constructs the grammar does not model cleanly (for example
  `select … done <<< ""` here-strings) fail closed with a parse error even when
  Bash itself accepts the line.
- **Text piped into a client.** `cat migration.sql | psql --dbname "$DATABASE_URL"` is
  allowed — the destructive SQL lives in a file the hook never reads. Same for
  `psql -f file.sql` and `mysql` file/stdin modes the hook does not model.
- **SQL client connection URLs.** Dynamic database URLs are permitted only after a
  proven connection-data option: `psql --dbname "$DATABASE_URL"` / `-d`, or
  `mysql --database "$DATABASE"`. One static positional dbname (`psql mydb -c …`)
  is allowed as connection data. A dynamic leading positional
  (`psql "$DATABASE_URL" -c …`) or unknown option before `-c` / `-e` is denied.
  MySQL `-p` / `--password` are optional attached-only flags (no separate
  operand); do not conflate them with psql `-p` (port).
- **Production db-applier / nonlocal DB escapes.** `scripts/db-applier.sh apply|restore`,
  `APPLY_SCHEMA=dangerous`, and `ALLOW_NONLOCAL_*` are denied at the hook.
  Local schema changes stay `pnpm db:push` / `pnpm db:push:dangerous`. The
  confirm-bound applier defends against mistakes and replay, not a driver
  holding production `DATABASE_URL`. Keep production credentials out of the
  agent's development environment. Deployment flags are workflow controls,
  not a credential boundary: Dokploy keeps one leader `safe` and followers
  `off` with `WAIT_FOR_SCHEMA=true`; other platforms use their documented
  lifecycle.
- **Indirection the hook cannot resolve** — opaque commands assembled through
  variables, piped or dynamically substituted `xargs` input, or scripts the
  bounded wrapper resolver does not model. A dynamic value in a supported
  inline shell-source role (`eval`, shell `-c`, or package call mode) is denied
  before reparse; dynamic ordinary arguments remain data, not interpreted code.
- **Shell function definitions** — `name() { … }` / `function name { … }` are
  rejected outright. The hook does not model defining a function and invoking it
  later; run the command directly instead.
- **`coproc`** — every coprocess definition (`coproc …`, including compound and
  named forms) is rejected outright. The hook does not model coprocess bodies;
  run ordinary commands directly instead. Quoted `coproc` text inside
  `echo`/`printf`/commit messages is not a denial.
- **Supported inline control forms** — `scripts/claude-hooks/bash-parser.mjs`
  parses complete Bash with Tree-sitter WASM, denies any `ERROR`/`MISSING` node
  or unclassified AST kind, and walks every executable `command`/`test_command`
  (including descendants inside `$(…)`, arguments, redirections, and control
  bodies). `for`/`select` iteration variables and `case` selector/pattern words
  are data, not commands. **Registered wrappers** (`timeout`, `stdbuf`, `xargs`,
  `setsid`, `exec`, `npx -p`, `pnpm exec`, …) are unwrapped with each tool's
  bounded argv grammar in `pre-tool-use.mjs`; unsupported wrapper spellings fail
  closed. **`env -S` / `--split-string` is explicitly rejected** — the hook does
  not unwrap or judge split-string shell text. **Nested shells** — `bash -c` /
  `sh -c` / `zsh -c` / `dash -c` / `ksh -c` / `ash -c` and `eval`
  payloads are re-entered only from statically known source words, up to three
  layers; the hook uses a finite per-dialect invocation profile rather than
  sharing option arity across shells. Zsh `-c` additionally admits only a
  portable static simple-command subset, so its distinct expansion language
  cannot be reinterpreted as Bash source. Unsupported advanced shell modes and
  deeper nesting fail closed. Opaque
  scripts, files passed to clients, and other non-inline programs are out of
  scope. Root `pnpm install` must succeed before the hook can load
  `web-tree-sitter` and `tree-sitter-bash`; any startup or WASM failure maps to
  deny (exit 2). Before dispatch, JSON payloads for matched `Bash` and
  Write/Edit tools must have their supported object shape (including a string Bash
  command or target path); malformed parsed requests deny with exit 2 rather than
  being treated as empty no-ops. Unknown named tools remain outside this hook's
  deliberately narrow contract.

`permissions.deny` (below) is the coarse second layer for exactly these gaps,
and `scripts/policy-checks.sh` is the commit-time backstop.

**Write / Edit and common static shell write targets:**

- `apps/web/src/routeTree.gen.ts`
- `.env.example`, `apps/web/.env.example`, `apps/native/.env.example`
- `CLAUDE.md`, `.cursorrules`, `.github/copilot-instructions.md`
- `pnpm-lock.yaml`
- policy enforcement assets: the hook parser/wrapper/template and installed
  `.claude/settings.json` / `.claude/settings.local.json`,
  `scripts/policy-checks.sh`, schema/access/secret
  policy gates and manifest, `lefthook.yml`, and the policy CI workflow

The hook also rejects direct static redirections (including enclosing
list/control/pipeline redirects), `tee`, in-place `sed`, `dd of=`, `ln`
destinations, `cp`/`mv`, common file-creation targets, `git rm`, archive
extract/`patch` at the project root, and direct removal or move-source operands
that name one of those enforcement assets or a containing directory. It resolves ordinary
relative and existing symlink paths against the project root; after a modeled
cwd change it compares a relative write against every protected file suffix and
a removal/move source against every protected file or containing-directory
suffix rather than guessing from just the basename. This is
intentional mistake prevention for direct tool operations, not tamper-proof
policy ownership: code with the same operating system identity can modify
repository files. Strong isolation must come from the external harness or OS.

`permissions.deny` in `.claude/settings.json` repeats the obvious prefixes
(`sudo:*`, `prisma migrate:*`, `dropdb:*`, `git reset --hard:*`,
`docker compose down -v:*`, the generated-file paths, …). Prefix matching is all
it can do — it cannot see a flag in the middle of a command — but it still
applies when hooks are turned off, which is why it is there.

## How to allow a blocked command

If a hook denied something you genuinely need:

1. Read the stderr message. Most denials name the allowed alternative
   (`pnpm db:push`, `pnpm db:push:dangerous`, `pnpm env:sync`,
   `pnpm sync:agent-docs`).
2. Run the allowed alternative yourself in a terminal, not through the agent.
3. Do not disable hooks to get past a denial. Be clear about what that does:
   `disableAllHooks` means this hook **does not run at all** — nothing is
   checked, and the only thing left is the `permissions.deny` prefix list.
   `--dangerously-skip-permissions` skips the permission prompts as well, so
   that list stops applying too. Neither is a "downgrade to a warning"; both
   remove the net. The only backstop still standing is
   `scripts/policy-checks.sh` at commit time, which cannot un-run a command.
4. If the denial is wrong (false positive), change the rule in
   `scripts/claude-hooks/pre-tool-use.mjs` and add the case to its self-test, in a
   reviewed PR — do not bypass it for one session.

## Cursor / Copilot cannot be blocked here

Those tools do not load `.claude/settings.json` and do not run PreToolUse
hooks. They can still type `git commit --no-verify` or `sudo …` into a
terminal the developer owns.

The repo refuses those strings when they land in `apps/`, `packages/`, or
`scripts/` via `scripts/policy-checks.sh`, which runs in:

- lefthook `pre-commit` (`policy-checks`)
- CI job **Policy checks** (`.github/workflows/pr-checks.yml`)

That is a commit-time backstop, not a tool-boundary block. It will not stop a
command that already ran. It will stop the invocation from being committed,
and CI will fail the PR if it was. For the workflow that compensates —
branch-per-change with `pnpm verify:fast` before merging to `main` — see
[agent-instructions.md § Branch workflow for harnesses without tool-boundary enforcement](./agent-instructions.md#branch-workflow-for-harnesses-without-tool-boundary-enforcement).
