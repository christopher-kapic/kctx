# Internationalization (i18n)

The starter ships a complete i18n surface: react-i18next for UI bundles, a custom URL-prefix router (`/$lang/...`), per-user persisted locale, a Zod v4 error map that translates validation messages automatically, and `pnpm i18n:translate`, which fills missing keys in the JSON locale bundles via OpenRouter (Claude Haiku 4.5 by default). Every URL is prefixed with a locale segment; every user-facing string lives in a JSON bundle, never inline in a component.

There is no content database. Page copy — including the landing page — is UI strings like everything else: it lives in `packages/locales/src/<lang>/common.json` under `home.*` and is translated by the same script. That is the deliberate trade: one store, one update path, no editing UI to operate or secure.

## Where things live

| Path | What it does |
|---|---|
| `apps/web/src/i18n/config.ts` | Re-exports `SUPPORTED_LOCALES` / `DEFAULT_LOCALE` + the `NAMESPACES` tuple |
| `apps/web/src/i18n/index.ts` | i18next init, eager default-locale bundle + on-demand `loadLocale()` for other locales, URL-path detector, language detection chain |
| `apps/web/vite.config.ts` | `manualChunks` rule grouping each non-default locale's namespace JSON into one `locale-<tag>` chunk |
| `apps/server/src/locale-modulepreload.ts` | Production: resolve the active non-default locale's chunk from the client Vite manifest for SSR `modulepreload` |
| `apps/web/src/i18n/zod.ts` | Locale-aware `z.config({ customError })` map (see "Zod validation messages") |
| `apps/web/src/i18n/labels.ts` | `LOCALE_LABELS` for the language switcher (kept in native script — not translated) |
| `apps/web/src/i18n/I18nReady.tsx` | Suspense boundary — gates the app on i18next init |
| `apps/web/src/i18n/redirect-to-default.ts` | Pure helper used by the `$lang` route to redirect unknown locales |
| `packages/locales/src/en-US/*.json` | UI string bundles (one file per namespace), in the shared `@starter/locales` package |
| `packages/locales/src/es-MX/*.json` | Same shape, translated |
| `packages/locales/src/native.ts` | Static `nativeResources` (Expo app, `native` namespace only) + `resolveDeviceLocale()` device-locale helper |
| `apps/web/src/hooks/use-user-locale-sync.ts` | Two-way `user.locale` sync in the `_app` branch: redirects signed-in users to their stored locale once on first load, and pushes an explicit localStorage choice (e.g. made on a session-free public page) up to the server |
| `apps/web/src/routes/$lang.tsx` | The locale-prefix layout — every other route nests under it; its `beforeLoad` validates the segment, loads the locale bundles, and swaps the active language on every navigation (the detector's `caches: ["localStorage"]` persists the choice) |
| `packages/config/src/locales.ts` | Shared `SUPPORTED_LOCALES` (imported by both web and API) |
| `packages/i18n-translate/` | Pluggable translation provider package (OpenRouter + Anthropic) |
| `packages/mailer/src/locales/{en-US,es-MX}/*.json` | Email-template bundles (`verify-email`, `invite-user`) |
| `packages/mailer/src/locales/index.ts` | `MAILER_LOCALES` list — kept in lockstep with `SUPPORTED_LOCALES` manually |
| `scripts/translate-locale-bundles.ts` | One-shot CLI behind `pnpm i18n:translate` — fills missing translations in the JSON bundles |

## Adding a new locale

Worked example: adding `fr-FR`. Six files to touch.

1. **Append the BCP 47 tag** to `SUPPORTED_LOCALES` in `packages/config/src/locales.ts`:
   ```ts
   export const SUPPORTED_LOCALES = ["en-US", "es-MX", "fr-FR"] as const;
   ```
2. **Mirror it in the mailer list** in `packages/mailer/src/locales/index.ts`:
   ```ts
   export const MAILER_LOCALES = ["en-US", "es-MX", "fr-FR"] as const;
   ```
3. **Add the display label** in `apps/web/src/i18n/labels.ts`:
   ```ts
   export const LOCALE_LABELS: Record<Locale, string> = {
     "en-US": "English (US)",
     "es-MX": "Español (México)",
     "fr-FR": "Français (France)",
   };
   ```
4. **Create the directories** so the locale globs find them:
   ```bash
   mkdir packages/locales/src/fr-FR
   mkdir packages/mailer/src/locales/fr-FR
   ```
   If the Expo app is kept, also add `packages/locales/src/fr-FR/native.json` (hand-translated — the native side has no lazy loading) and extend `nativeResources` in `packages/locales/src/native.ts`.
   The new locale loads on demand — only `DEFAULT_LOCALE` is bundled eagerly; every other locale's namespace JSON is grouped by a `manualChunks` rule into a single `locale-fr-FR` chunk, fetched via `loadLocale()` when it becomes active. Adding a language therefore costs nothing in the base bundle, costs one request on first visit, and needs **no** bundler or per-locale module change — the glob and the chunk rule both pick the folder up automatically. After a production build the chunk appears in `apps/web/dist/client/.vite/manifest.json` and the API server modulepreloads it on `/fr-FR/...` SSR. If you ever change `DEFAULT_LOCALE`, update the pinned eager glob and the negative lazy-glob pattern in `i18n/index.ts` (a dev-time `console.warn` flags the mismatch). See [performance-and-bundling.md § i18n locale splitting](./performance-and-bundling.md).
5. **Generate the UI bundles** against the new target:
   ```bash
   pnpm i18n:translate -- --target fr-FR
   pnpm i18n:translate:mailer -- --target fr-FR
   ```
   Both commands are idempotent and skip already-populated keys, so re-running them in CI is safe.
6. **Review the generated copy** for the surfaces a visitor lands on first — the `home.*` keys in `common.json` carry the landing page, and machine translation of marketing-tone copy is worth a human pass.

No DB migration needed — `User.locale` is a free-form `String` column validated at the API boundary by `SUPPORTED_LOCALES`.

**Adding a non-Latin-script locale (Cyrillic, Greek, CJK, Arabic, …)?** The font (`@fontsource-variable/roboto`) ships every script as a separate `unicode-range` subset that loads on demand, so text still renders correctly with no extra work. But the root route only **preloads the Latin subset** (`apps/web/src/routes/__root.tsx`) — the one every shipped locale uses today. A non-Latin locale's subset will load slightly later (discovered when the CSS parses, not preloaded in parallel). If that locale becomes a primary audience, add a second `<link rel="preload">` for its subset alongside the Latin one, following the rules in [performance-and-bundling.md § Font preloading](./performance-and-bundling.md#font-preloading) (exact-URL match, `crossOrigin: "anonymous"`). RTL scripts (Arabic, Hebrew) additionally need `dir="rtl"` handling, which this template does not ship.

## Using `t()` in components

Standard react-i18next. Always pass an explicit namespace list, even when one suffices — it makes dependencies obvious to readers and to the JSON-bundle scanner.

```tsx
import { useTranslation } from "react-i18next";

export function DashboardHeader() {
  const { t } = useTranslation(["dashboard", "common"]);
  return (
    <header>
      <h1>{t("dashboard:welcome", { name: user.name })}</h1>
      <button>{t("common:actions.save")}</button>
    </header>
  );
}
```

Key conventions:

- **Dot paths under nested objects** in JSON. `common:actions.save` reads `common.json → actions.save`.
- **ICU placeholders** use `{{name}}` (i18next's default). Pass values as the second arg: `t("welcome", { name })`.
- **Embedded JSX** uses `<Trans>` with the **`components` array prop**, not JSX children. The JSON value is the source of truth for both text and numbered tag positions; the array maps each `<N>` to a JSX element by index.

  ```tsx
  import { Trans } from "react-i18next";

  // JSON: "agreedToTerms": "I agree to the <0>Terms</0> and <1>Privacy Policy</1>."
  <Trans
    i18nKey="auth:agreedToTerms"
    t={t}
    components={[<a key="0" href="/terms" />, <a key="1" href="/privacy" />]}
  />;
  ```

  Do **not** pass JSX children with numbered tags (`<Trans i18nKey="…" t={t}>I agree to the <0>Terms</0>…</Trans>`). React-i18next's child-positional matching is brittle: a leading text node shifts every index, causing duplicated phrases or dropped tag content. The bundle-translation script preserves `<N>` tags during translation, so the components array stays in sync across locales.

  Do **not** pass `components` as an object keyed by index (`components={{ 0: <code /> }}`). React-i18next treats objects as named-tag maps (`<code>…</code>`), not numbered-tag maps. Use an array.

## Naming conventions

- **Namespaces**: `common`, `auth`, `errors`, `validation`, `admin`, `chat`, `consent`, `dashboard`, `settings`, `nav`. One JSON file per locale. The Expo app adds `native`. Full list: the `NAMESPACES` tuple in `apps/web/src/i18n/config.ts` — trust the tuple, not this sentence.
- **Keys**: dot paths under nested objects. Group by surface (`actions.save`, not `saveAction`).
- **Per-route namespaces**: only when a single route owns more than ~20 unique strings. Otherwise live under `dashboard`, `settings`, `admin`, etc.
- **camelCase keys**, not `snake_case` or `kebab-case`. The Zod error-map keys (`tooSmall.string`, `invalidString.email`) are the convention.
- **A new web namespace needs no per-locale wiring.** Add `<ns>.json` for every locale (`pnpm i18n:translate` fills the non-default ones) and add the name to the `NAMESPACES` tuple. The eager default-locale glob, the lazy non-default globs, and the `locale-<tag>` chunk rule all match by directory, so nothing has to be registered per locale.

## The no-hardcoded-strings rule

User-facing strings in components and routes **must** go through `t()`. Exceptions (mirroring the `AGENTS.md` Content rule):

1. **Form labels tied to a specific control.** The visible `<label>` text for one input may live next to the control it names. Validation copy is **not** covered by this exception — see § Zod validation messages below, which is the single source for how validation strings are written.
2. **System fallback errors.** Network failures, 5xx fallbacks, and "Try again" buttons can stay hardcoded — last-resort copy that fires when i18n itself may be broken.
3. **Accessibility text.** `aria-label`, `alt` for icon-only controls, and screen-reader-only labels can be inline when they describe a control whose visible glyph is universal (a magnifying glass for "Search"). Prefer `t()` when surrounding copy is already translated.

A fourth case is the signal to add a translation key, not an exception.

## Zod validation messages

Validation messages flow through the global error map at `apps/web/src/i18n/zod.ts`. It binds Zod v4's `z.config({ customError })` to the `validation` namespace, swaps closures on every `languageChanged` event, and is installed once during i18next init.

**Use bare validators.** Do not inline custom messages — they bypass the error map.

```ts
// Good — message comes from validation:tooSmall.string and switches with the locale.
const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

// Bad — the inline string is hardcoded English forever.
const schema = z.object({
  email: z.string().email("Please enter a valid email address"),
});
```

If you genuinely need a custom message (a domain-specific rule), add a key to `validation.json`:

```json
// packages/locales/src/en-US/validation.json
{
  "domainAllowList": "Email must end in @example.com"
}
```

Then reference it from the schema via `.refine`:

```ts
import { useTranslation } from "react-i18next";

const { t } = useTranslation("validation");
const schema = z.string().email().refine(
  (v) => v.endsWith("@example.com"),
  { message: t("domainAllowList") },
);
```

The error-map covers `invalid_type`, `too_small`, `too_big`, `invalid_format`, `invalid_value`, `not_multiple_of`, `unrecognized_keys`, `invalid_union`, `invalid_key`, `invalid_element`, and `custom`. Add keys to `validation.json` to override defaults — the map looks them up dynamically.

## One store, one update path

Every user-facing string lives in `packages/locales/src/<lang>/*.json` (the shared `@starter/locales` package), edited by hand or filled in by the bundle-translation script. The default locale ships in the base bundle; other locales are split into per-locale chunks and loaded on demand (see [performance-and-bundling.md](./performance-and-bundling.md)).

That includes page copy. The landing page's headline, subhead, and CTA are `home.*` keys in `common.json`, not rows in a content table — so changing marketing copy is a commit, reviewed and deployed like any other change, and translated by the same idempotent script.

**If the product genuinely needs editor-authored content** — a blog whose posts are written weekly by someone without repo access — that is a database feature, not a locale-bundle key. Do not smuggle it in as a growing `common.json`. Bundles are loaded in full per locale and shipped to every visitor; they are sized for UI strings. The maintained recipe is [add-ins/cms.md](./add-ins/cms.md).

## Translation provider

Pluggable via `packages/i18n-translate`. Default: **OpenRouter** with the `anthropic/claude-haiku-4-5` model. Two ways to swap:

- **Different provider** — set `TRANSLATION_PROVIDER=anthropic` to call the Anthropic SDK directly. Requires `ANTHROPIC_API_KEY`.
- **Different model on OpenRouter** — set `TRANSLATION_MODEL=google/gemini-2.5-flash` (or any OpenRouter slug). Keep `TRANSLATION_PROVIDER=openrouter`.

Provider construction is cached after first call, so one `pnpm i18n:translate` run reuses a single HTTP client across every namespace. The factory throws a clear error on first use if the chosen provider's API key is missing — surfacing the misconfig at the start of the run rather than swallowing it. The only consumer today is `scripts/translate-locale-bundles.ts`; nothing in the server or worker runtime calls it. Restoring the CMS add-in ([add-ins/cms.md](./add-ins/cms.md)) makes the `translate-content` worker a second runtime consumer of the same factory.

To add a third provider, implement `TranslationProvider` from `packages/i18n-translate/src/types.ts`, register it in `factory.ts`, and add the discriminator to the `TRANSLATION_PROVIDER` enum in `packages/env/src/vars/shared.ts` (the worker-safe declarations — **not** `vars/server.ts`; `@starter/i18n-translate` imports `@starter/env/shared`, so a value added to `server.ts` would be `undefined` at translation time).

## The bundle-translation script

`pnpm i18n:translate` translates `packages/locales/src/en-US/*.json` into `packages/locales/src/<target>/*.json`. Default target is `es-MX`.

```bash
pnpm i18n:translate                  # fill missing only (default: en-US -> es-MX)
pnpm i18n:translate -- --force       # re-translate every key, overwriting existing
pnpm i18n:translate -- --ns common,auth   # subset of namespaces
pnpm i18n:translate -- --target fr-FR     # different target locale
pnpm i18n:translate -- --strict      # drop keys whose ICU placeholders fail validation

pnpm i18n:translate:mailer           # same, for packages/mailer/src/locales/
```

Default behavior is **idempotent**: keys already present in the target are skipped. Run it as often as you like; only new keys hit the provider. The script bundles one call per namespace (one round-trip per file) and validates that ICU placeholders + `<Trans>` numeric tags survive the round-trip.

## URL routing

Every route is nested under `/$lang/...`. The locale segment is mandatory, validated by the `$lang` layout (`apps/web/src/routes/$lang.tsx`).

**Detection chain** (priority order):

1. **URL path segment** — `/es-MX/dashboard` always wins. The `urlPath` detector in `apps/web/src/i18n/index.ts` reads `window.location.pathname.split("/")[1]`.
2. **localStorage** — explicit "I picked this locale on this device" via the language switcher (key: `locale`).
3. **`user.locale`** — for signed-in users, `useUserLocaleSync()` navigates to `/${user.locale}/...` once on first load if localStorage is empty.
4. **`navigator.language`** — the browser/OS UI language.
5. **`DEFAULT_LOCALE`** — `en-US`.

**Redirect rules** (enforced by `decideLocaleRedirect`):

- Visit `/dashboard` (no prefix) → 302 to `/${DEFAULT_LOCALE}/dashboard`.
- Visit `/xx-XX/dashboard` (unsupported locale) → 302 to `/${DEFAULT_LOCALE}/dashboard` (the unknown segment is stripped).
- Visit `/foo/bar` where `foo` doesn't look like a locale → 302 to `/${DEFAULT_LOCALE}/foo/bar` (path preserved).

Search params and hash are preserved across the redirect.

## Cost

At template-typical scale: a full UI-bundle translation (~766 leaf keys across the web namespaces, or ~836 including `native.json`, × 1 target locale) costs roughly **$0.07** with `anthropic/claude-haiku-4-5` via OpenRouter. The one-time fill across four target locales is ~$0.30, and incremental runs only pay for keys you have added since the last one — which is the normal case, since the script is idempotent.

Translation is a build-time cost here, not a per-request one: nothing translates in response to user traffic, so the bill cannot be driven by visitors. Still set **provider-side spend limits** in OpenRouter or Anthropic before handing the key to CI. This template documents expected costs and lets you disable the provider by removing the API key, but it does not ship an in-app LLM budget system.
