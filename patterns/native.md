# Native App

The native app in `apps/native` is a managed Expo app using Expo Router, React Native, Uniwind, HeroUI Native, Better-Auth's Expo client, and the same `@starter/api` oRPC router as the web app.

Read this before changing mobile code. Most mistakes here come from applying browser assumptions to native.

The native app is a **removable module**. If the product is web-only, remove it via [removable/native.md](./removable/native.md) — ideally during getting-started Phase 5, before feature work.

## Hard Rules

- Keep the app managed Expo by default. Do not run `expo prebuild`, add `apps/native/ios`, or add `apps/native/android` unless the user explicitly chooses a bare/prebuild workflow.
- Do not upgrade Expo, React, React Native, Reanimated, Screens, Gesture Handler, Worklets, or Expo modules piecemeal. Treat them as an Expo SDK set and update them together.
- Keep native dependencies in the pnpm catalog. The app package should use `"catalog:"` except for deliberate Expo SDK peer pins such as React / React DOM when the managed SDK requires a coordinated version.
- Do not replace `@better-auth/expo` with browser cookie handling. Native does not have browser-managed cookies.
- Do not remove the manual `Cookie` header forwarding in `apps/native/utils/orpc.ts`. Better-Auth Expo stores the session cookie and `authClient.getCookie()` is what lets authenticated oRPC procedures work on iOS/Android.
- Do not use `window.location.origin`, Vite env vars, or the Vite dev proxy in native code. Native reads `EXPO_PUBLIC_SERVER_URL` from `@starter/env/native`.
- Do not put secrets in `EXPO_PUBLIC_*`. Expo public env vars are bundled into the app.
- Do not import the web image-prepare helper (`@starter/api/lib/asset-image-prepare`) in `apps/native` — it is canvas/WASM browser code and Metro would try to resolve the embedded `heic-to` decoder. Native image handling uses Expo ImagePicker + ImageManipulator instead.
- Preserve `metro.config.js`, `global.css`, and `uniwind-env.d.ts` as load-bearing styling infrastructure. `uniwind-types.d.ts` is generated by Metro and intentionally gitignored.

## Local Development

Run the API and Expo app separately:

```bash
pnpm dev:server
pnpm dev:native
```

`pnpm dev:native` runs `pnpm doctor:native` first. The doctor fails when:

- `apps/native/.env` is missing,
- `EXPO_PUBLIC_SERVER_URL` is missing, invalid, or includes a path/query/hash,
- generated `apps/native/ios` or `apps/native/android` directories exist.

Use the right API origin for the target. Do not include a path, query string, or hash:

```env
# iOS simulator with raw local server
EXPO_PUBLIC_SERVER_URL=http://localhost:3000

# Android emulator with raw local server
EXPO_PUBLIC_SERVER_URL=http://10.0.2.2:3000

# Physical device
EXPO_PUBLIC_SERVER_URL=http://<your-lan-ip>:3000
```

Physical devices cannot reach your laptop's `localhost`. Use a LAN IP or a tunnel.

Expo web is different from iOS/Android because it runs in the browser. If `pnpm native:web` serves from an origin other than the API origin, set the root `.env` `CORS_ORIGIN` to the exact Expo web origin printed by the CLI. The server uses `CORS_ORIGIN` for both Hono CORS and Better-Auth trusted origins.

Target helpers stay in the managed workflow:

```bash
pnpm native:ios
pnpm native:android
pnpm native:web
```

These run `expo start --ios`, `expo start --android`, and `expo start --web`. They must not create `apps/native/ios` or `apps/native/android`.

## App identity

`apps/native/app.json` ships with the placeholder identity `"name": "Starter"` / `"slug": "starter"`. The scheme derived from the slug is load-bearing (OAuth trusted origins, Cookie forwarding), so when you rebrand, change `name` and `slug` **together** with the scheme-dependent wiring in `lib/auth-client.ts` — see [agent-tasks/rebrand.md](./agent-tasks/rebrand.md) for the display-side rename flow.

## Auth And API

The native app has two clients:

- `apps/native/lib/auth-client.ts` creates the Better-Auth client with `expoClient`, `SecureStore`, and the Expo scheme from `app.json`.
- `apps/native/utils/orpc.ts` creates the oRPC client. On native platforms it sets `credentials: "omit"` and forwards `Cookie` from `authClient.getCookie()`. On web it uses `credentials: "include"`.

That platform split is intentional. Changing it usually breaks authenticated procedures on either native or web.

The template's native auth surface is intentionally minimal: email/password sign in, two-factor sign-in, a "Forgot password?" affordance that requests a reset email (completion happens on the web via the emailed link — native never does token entry), optional sign up, sign out, and clear verify-email messaging after signup. The full web app still owns richer auth UX such as SSO, redirects, and account security settings. When `FORCE_SSO=true`, native blocks the email/password forms and tells the user to use the web app until product-specific native SSO is added. Add those native flows only after onboarding notes say the product needs them. Every string in this surface (including the Zod validation messages, built via `makeSignInSchema(t)` / `makeSignUpSchema(t)` factories) is localized through the `native` namespace — see Template Surface below.

### Adding native SSO (recipe — not implemented in the template)

The server currently contains **zero** native-specific auth code, which is what keeps [removable/native.md](./removable/native.md) a clean leaf-deletion. Native SSO is the first feature that changes that, so implement it deliberately:

1. **Server plugin.** Add the Expo plugin to `packages/auth/src/index.ts`:

   ```ts
   import { expo } from "@better-auth/expo";
   // in the betterAuth({ plugins: [...] }) list:
   expo(),
   ```

   `@better-auth/expo` is already in the pnpm catalog (the native app uses its client half). Add it to `packages/auth/package.json` as `"catalog:"`. From this point, `packages/auth` depends on the native module — note it in the removal doc if you later rip native out.

2. **Trust the app scheme.** OAuth callbacks redirect to the app's deep link, and Better-Auth rejects redirect targets that aren't trusted origins. Add the scheme from `apps/native/app.json` to `trustedOrigins`:

   ```ts
   trustedOrigins: [...existing, "starter://"], // your rebranded scheme
   ```

   Never add a wildcard scheme. If you support Expo Go during development, you also need the `exp://` dev-client origin — gate that on `NODE_ENV !== "production"`.

3. **Client flow.** Better Auth 1.7 folded generic OAuth into the standard social client path, so the native client uses `signIn.social` (no `genericOAuthClient()`). Trigger sign-in with the deep-link callback:

   ```ts
   await authClient.signIn.social({
     provider: "sso",
     callbackURL: "/(tabs)", // resolved against the app scheme by the expo client
   });
   ```

   `expo-web-browser` (already a dependency) opens the IdP session; on redirect the expo client stores the session cookie in `SecureStore` exactly like email/password sign-in.

4. **Verify on a device or simulator** against a real IdP (`SSO_*` env vars set, `SSO_ENABLED=true`): complete the browser round-trip, confirm the session lands (`authClient.useSession()`), then kill and relaunch the app to confirm the `SecureStore` cookie survives. Also verify sign-out clears it.

5. **Update the `forceSso` branch** in `apps/native/app/(tabs)/account.tsx` to render the SSO button instead of the "use the web app" message.

For data fetching, use the same oRPC query utilities as the web app:

```tsx
const health = useQuery(orpc.health.check.queryOptions());
const privateData = useQuery({
  ...orpc.privateData.queryOptions(),
  enabled: !!session?.user,
});
```

Gate conditional queries with `enabled`; do not call hooks conditionally.

## Template Surface

Keep `apps/native` small and product-neutral:

- Home tab: API reachability, feature flags, protected-procedure example, pull-to-refresh via `RefreshControl` passed through `Container`'s `scrollViewProps`.
- Account tab: sign in, optional sign up based on server config, sign out, and a "Forgot password?" affordance on the sign-in form that requests a reset email (a local card state like the 2FA one — no new screen; the reset is completed on the web). Session restore and app-config loads render `Skeleton` placeholders, not spinners, matching the web rule.
- Theme toggle in the tab header.
- Haptics go through `haptic()` in `apps/native/lib/haptics.ts` — native-only (the web app has no haptics). The canonical preset list lives in [animation § Haptic presets](./animation.md#haptic-presets); native implements `"light"`, `"success"`, `"error"`, `"selection"`, and `"warning"`. It no-ops on Expo web. Do not call `expo-haptics` directly from screens.
- i18n: the native app is localized, not English-only. It initializes i18next in `apps/native/lib/i18n.ts` from the shared `@starter/locales` package (`native` namespace only — Metro can't code-split, so web namespaces like `admin`/`marketing` are never bundled) and picks the device locale via `expo-localization` (`resolveDeviceLocale()` — exact tag match, then language-prefix match, then `DEFAULT_LOCALE`). Every user-facing native string goes through `t("native:…")`. When you add or change native copy, add the English key to `packages/locales/src/en-US/native.json` and then run `pnpm i18n:translate` — the script globs every `*.json` in the source locale directory and excludes nothing by default, so `native.json` is filled in along with the web namespaces (use `--exclude-ns native` to opt out, or `--ns native` to do only it). Every other locale must end up with the key: there is no on-demand loading on native, so a missing key renders the raw key string. Locale constants stay in `@starter/config/locales`.

Avoid adding sample screens, decorative demos, fake data, or marketing copy to the template. Add product screens only after the app's `notes/` onboarding describes what users need.

## Verification

Before handing off native changes, run:

```bash
pnpm doctor:native
pnpm --filter native check-types
pnpm check:ci
pnpm doctor:react
```

react-doctor scans the native app too (see AGENTS.md → React health checks). React Compiler is enabled here, so its compiler-compatibility diagnostics are errors: no `try` statements inside components (use `.catch()` on the promise), no manual `useMemo`/`useCallback`, and always destructure `useQuery` results instead of holding the whole query object.

Run the full workspace type check when shared packages or root config changed:

```bash
pnpm check-types
```
